# The isolated test stack

Owner, 2026-11-27: "Create an isolated testing database rather than repeatedly
writing to the production database. Use dedicated test accounts, deterministic
fixtures, and automated cleanup."

`tests/isolated/up.sh` starts, in containers on this machine:

| Piece | Image | What it is |
|---|---|---|
| database | `supabase/postgres` (Postgres 17) | empty, then given `schema.sql` |
| auth | `supabase/gotrue` | sign-up, sign-in, password reset, account deletion |
| REST | `postgrest/postgrest` | what the app's storage layer and the integrity run's database checks read |
| gateway | `gateway.mjs` | the one address a Supabase client is given |

and creates the two test accounts the fixtures already use (same ids and
sign-ins as `tests/smoke/fixture/account.ts`). Keys and passwords are minted
per run into `.run/` (not committed). `down.sh` removes everything.

```bash
tests/isolated/up.sh
set -a; . tests/isolated/.run/app.env; set +a
PORT=5199 npm run dev &                                   # the app, from this checkout
npx tsx tests/isolated/schema-check.ts                    # the schema the code expects is there
npx tsx tests/integrity/run.ts --only '^(?!chat)' --out test-results/integrity-isolated
tests/isolated/down.sh
```

CI runs exactly this on every push to a working branch and on every pull
request (`.github/workflows/integrity-isolated.yml`).

## What it is, and is not

- **No production row is in it.** `schema.sql` is the production schema's
  STRUCTURE only (tables, constraints, indexes, functions, triggers, row-level
  security policies, grants), generated by `dump-schema.sql`. Compared after
  applying: 51 tables, 601 columns, 221 indexes, 159 policies, 11 functions,
  40 triggers, 174 constraints — identical to production (2026-11-27).
- **It cannot fall behind silently.** `schema-check.ts` asks the app's own
  diagnostic (`GET /api/diagnostics/schema`), which lists everything a
  migration adds; CI fails if the isolated schema lacks any of it. After a
  new migration is applied to production, regenerate `schema.sql`.
- **Not in the stack:** the AI provider (chat scenarios need its key; they run
  against the deployed app with the smoke account), file storage (uploads),
  bank connections, e-mail delivery (sign-ups are confirmed automatically).

## Regenerating `schema.sql`

Run `dump-schema.sql` against production (it only reads the catalog) and save
its single text result as `schema.sql`. It contains no rows and no secrets;
`tests/ops-guards.test.ts` scans the repository for credentials as before.
